

**Hierarchical Z-Buffer (Hi-Z / 层级深度缓冲)** 是现代高性能图形编程（尤其是 **GPU-Driven Pipeline**）中真正的“大杀器”。

如果说 Occlusion Query 是“问单个问题”，Software Occlusion 是“CPU 模拟”，那么 **Hi-Z 就是“GPU 的二分查找法”**。它将深度测试的效率从线性（逐像素查）提升到了对数级（逐区域查）。

它是实现《刺客信条：大革命》、《荒野大镖客2》以及 Unreal Engine 5 **Nanite** 系统超高效率剔除的核心基石。

---

### 1. 核心痛点：逐像素对比太慢了

在传统的 Z-Buffer 算法中，要判断一个物体（比如一个箱子）是否被前面的墙挡住，GPU 必须做以下事情：
1.  把箱子光栅化成 1000 个像素。
2.  去读取这 1000 个像素对应位置的深度缓冲值。
3.  如果不做优化，需要读 1000 次显存。

**Hi-Z 的核心思想**：
如果我知道这一块 8x8 的区域里，**最远（Max Depth）** 的深度是 10 米，而我的箱子在 20 米远。那我根本不需要一个像素一个像素地去比。**哪怕只比一次，我就知道这 64 个像素全都被挡住了。**

---

### 2. 数据结构：深度金字塔 (Depth Pyramid)

Hi-Z 本质上是一张**带 Mipmap 链的深度纹理**。

*   **Mip Level 0**：原始分辨率（例如 1024x1024）。存储原始深度。
*   **Mip Level 1**：512x512。每个像素对应 Level 0 中的 2x2 区域。
*   **Mip Level 2**：256x256...
*   ...
*   **Mip Level N**：1x1。整个屏幕的深度极值。

#### 生成规则 (Downsampling)
这是最关键的一步。生成下一级 Mip 时，取上一级对应 4 个像素的 **最远深度值 (Max Depth)**。
*   *为什么取最远？* **保守策略（Conservative）**。
*   假设一个 2x2 区域里，3 个像素是前面的墙（深度 5米），1 个像素是墙上的洞（可以看到后面 100米 的山）。
*   生成的 Hi-Z 像素必须记录 **100米**。
*   如果不记录 100米而记录 5米，当我们有个物体在 50米处时，算法会误以为被 5米的墙挡住了，导致物体被错误剔除（实际上应该透过那个洞看到它）。

---

### 3. Hi-Z 剔除算法流程

有了这张金字塔图，剔除逻辑就变得极其优雅：

#### 第一步：计算包围盒 (Screen Space AABB)
把物体的包围盒投射到屏幕上，算出它占了多大面积。比如是 `60 x 60` 像素。

#### 第二步：选择 Mip Level
我们在 Hi-Z 金字塔里找一层，使得该层的纹素大小刚刚好能覆盖的一大部分。
*   通常选择公式：`Level = log2(Box_Size)`。
*   对于 60x60 的物体，我们可能选 Level 5 或 6（纹素对应屏幕的 32x32 或 64x64）。

#### 第三步：采样 4 次 (The 4-Tap Fetch)
不管物体在屏幕上有多大（哪怕占满屏幕），我们只需要在这个 Mip Level 上采样 **4 个纹素** 就能覆盖住这个物体所在的区域。

#### 第四步：比较深度
*   **物体深度**：计算物体包围盒的**最近深度 (Closest Depth)**。
*   **遮挡深度**：取那 4 个纹素中的**最远深度 (Max Depth)**。
*   **判断**：如果 `物体最近深度 > 遮挡最远深度`，说明物体**完全**被挡住了。 -> **剔除！**

### 4. 为什么 Hi-Z 比 GPU Query 快？

这通常是让人困惑的地方：*“GPU Query 也是 GPU 做的，Hi-Z 也是 GPU 做的，凭什么 Hi-Z 快？”*

1.  **无状态切换，无延迟**：
    *   **GPU Query**：需要 CPU 发命令 -> GPU 画 -> GPU 存计数器 -> CPU 读回（延迟）。
    *   **Hi-Z Culling**：通常写在 **Compute Shader** 里。
        *   CPU 把 10,000 个物体的包围盒数据打包成一个 Buffer。
        *   启动 Compute Shader。
        *   GPU 线程并行读取 Hi-Z 纹理（Texture Fetch），并行计算剔除。
        *   输出结果直接生成 `IndirectDrawArgs` 或者压缩后的 `Instance Buffer`。
        *   **GPU 直接拿着剔除后的结果去渲染，CPU 全程不需要读回任何数据！**（彻底消灭了 CPU-GPU 同步开销）。

2.  **带宽极低**：
    *   查询一个巨大的物体，只需要读 4 次纹理。这比光栅化成千上万个像素去写入 Z-Buffer 要快几个数量级。

### 5. 硬件 Hi-Z vs 软件 Hi-Z

这是一个进阶概念，防止混淆：

#### A. 硬件 Hi-Z (Hardware Early-Z / Z-Cull)
这是**显卡驱动和硬件内部**自带的功能，你不需要写代码，它就在运行。
*   现代 GPU（Nvidia/AMD/Mali/Adreno）在光栅化之前，内部有专用的电路维护一个粗糙的 Hi-Z 表。
*   **作用**：当你画一个三角形时，GPU 硬件会自动查表，如果发现被挡住，这就直接丢弃，不进 Pixel Shader。
*   **限制**：这对“不画像素”有帮助，但它**不能减少 Draw Call**。CPU 还是得把命令发给 GPU，GPU 拿到后才发现“哦，不用画”。CPU 的开销依然存在。

#### B. 软件/Compute Hi-Z (我们讨论的这个)
这是**程序员**（引擎开发者）手动实现的技术。
*   利用 Compute Shader 读取上一帧生成的深度金字塔。
*   **作用**：直接剔除 Draw Call / Instance。被剔除的物体，其 Draw 命令根本不会生成，或者 Instance 数量直接变少。
*   **优势**：同时节省了 CPU 的 Draw Call 开销和 GPU 的渲染开销。

---

### 6. 总结：Hi-Z 在大世界渲染中的地位

如果你的游戏是《绝地求生》或《塞尔达》这种：

1.  **PVS**：没用（大平原）。
2.  **GPU Query**：慢，有延迟，物体多了 CPU 发 Query 命令都发不过来。
3.  **Software Occlusion**：CPU 压力大。

**只有 Hi-Z 是终极解法：**
1.  **Pre-pass**：先快速画一遍地形和大建筑，生成深度缓冲。
2.  **Build Hi-Z**：用 Compute Shader 把深度缓冲降采样生成金字塔（耗时极短，0.x 毫秒）。
3.  **Cull**：启动 Compute Shader，几万个草丛、石头、敌人的包围盒扔进去，对着 Hi-Z 纹理一查。
4.  **Draw**：输出真正需要画的物体列表，GPU 也就画那几千个。

**一句话总结：**
Hi-Z 是利用**降采样（Mipmap）**和**Compute Shader**，让 GPU 自己查阅一张“全局概览图”，从而在 GPU 内部自行决定“谁该死，谁该活”，彻底解放 CPU。
