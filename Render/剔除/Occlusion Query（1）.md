

**Occlusion Query (遮挡查询)** 是图形学中一个非常底层的、由 **GPU 硬件直接支持** 的功能。

如果说 PVS 是“查表”，Software Occlusion 是“CPU 模拟”，那么 **Occlusion Query 就是“问显卡本人”**。

它是现代游戏引擎（Unity / Unreal / CryEngine）中除了 PVS 之外最重要的剔除手段，也是实现许多高级特效（如镜头光晕 Lens Flare）的核心技术。

---

### 1. 核心原理：显卡帮你看一眼

Occlusion Query 的工作流程非常直观，就像是你（CPU）在指挥画家（GPU）画画时，问了他一个问题。

#### 步骤详解：

1.  **CPU 下达命令**：
    *   CPU 告诉 GPU：“嘿，我要画一个物体（通常是一个简化的包围盒），但我**并不想让它真的出现在屏幕上**（关闭颜色写入和深度写入）。”
    *   CPU 发起查询指令：`glBeginQuery(GL_SAMPLES_PASSED, queryID)` 或 `D3D11_QUERY_OCCLUSION`。

2.  **GPU 执行光栅化**：
    *   GPU 像往常一样处理这个物体的顶点，把它光栅化成像素（Fragment）。
    *   **关键点**：GPU 会把这些像素和当前帧缓冲（Frame Buffer）里的 **深度缓冲（Z-Buffer）** 进行对比（Depth Test）。

3.  **GPU 统计结果**：
    *   GPU 内部有一个计数器。每当有一个像素**通过了深度测试**（说明它没被前面的物体挡住，是可见的），计数器就 +1。
    *   如果有 100 个像素通过了测试，那结果就是 100。
    *   如果结果是 0，说明这个物体的所有像素都被前面的墙挡住了。

4.  **CPU 获取结果**：
    *   CPU 结束查询：`glEndQuery(GL_SAMPLES_PASSED)`。
    *   CPU 问 GPU：“刚才那个包围盒，你能看见几个像素？”
    *   GPU 回答：“50 个” 或者 “0 个”。

### 2. 致命缺陷：回读延迟（Readback Latency）

听起来很完美对吧？既然显卡算得这么快，为什么我们还要搞 PVS 和软件剔除？

这就涉及到了 GPU 架构的一个核心特性：**流水线与异步执行**。

*   **CPU 的节奏**：CPU 下达渲染命令的速度极快，它把命令扔进一个“命令缓冲区”（Command Buffer），然后就去处理下一帧逻辑了，根本不等待 GPU 画完。
*   **GPU 的节奏**：GPU 按照自己的频率，忙着执行缓冲区里的命令。当 CPU 发出 Query 时，GPU 可能正在画上一帧的阴影，还没轮到这个 Query。

**导致的后果**：
1.  CPU 发出 Query。
2.  CPU 想要结果。
3.  **但是 GPU 还没算完！**
4.  **死锁（Stall）**：如果 CPU 此时非要等结果（强制同步），CPU 就会停下来什么都不做，直到 GPU 算完返回数据。这两个本来是并行工作的硬件，突然变成了串行，这会造成巨大的性能卡顿（FPS 骤降）。

---

### 3. 工业界的解决方案：虽然有延迟，但能用

为了避免“死锁”，聪明的工程师们发明了几种策略：

#### A. “上一帧的数据给这一帧用” (History Propagation)
*   **逻辑**：
    *   **第 1 帧**：CPU 发出查询：“这个房子可见吗？”（但不等结果，默认它是可见的，先画出来）。
    *   **第 2 帧**：CPU 去读第 1 帧查询的结果。GPU 说：“第 1 帧的时候它是不可见的（0像素）”。
    *   **第 3 帧**：既然第 1 帧不可见，那我就**不再渲染这个房子了**。
    *   **同时**：依然发射一个查询，看看它现在是否可见了。

*   **缺点**：
    *   **物体闪烁（Popping）**：如果你快速转头，物体可能在第 1 帧没画（因为第 0 帧不可见），但第 1 帧它其实跑出来了。这就导致物体会“迟到一帧”才出现。
    *   **解决办法**：把包围盒做大一点（Conservative），或者结合视锥体预测。

#### B. 条件渲染 (Conditional Rendering / Predicated Rendering)
*   这是现代 API（DX11/12, Vulkan, OpenGL 4.x）的高级功能。
*   **逻辑**：
    *   CPU 说：“显卡大哥，这是一个 Query。接下来这一堆复杂的模型，**只有当刚才那个 Query 的结果大于 0 时，你才画它们**。”
    *   CPU **完全不读回结果**，直接把判断逻辑交给 GPU 内部调度。
*   **优点**：彻底没有 CPU-GPU 同步延迟！
*   **缺点**：并不是真的“不画”，GPU 前端的命令处理器（Command Processor）依然要处理这些命令，只是不执行光栅化。对于极复杂的场景，收益巨大；对于简单物体，可能本身开销还没命令开销大。

---

### 4. Occlusion Query 的应用场景

除了做剔除，它还有一个极其常见的用途：**镜头光晕（Lens Flare）**。

*   **问题**：当太阳被墙挡住时，镜头光晕应该消失；当太阳露出来时，光晕应该出现。
*   **实现**：
    1.  在太阳的位置画一个小方块（不可见，只做 Query）。
    2.  如果 Query 返回的像素数 > 0，说明太阳没被挡住。
    3.  根据像素数的多少（可见面积），调整光晕的亮度（Alpha值）。
    *   这就是为什么你在游戏中，看着太阳慢慢躲到山后，光晕是**渐隐**的，而不是突然消失的，因为 Query 返回的像素数是逐渐减少的。

---

### 5. 总结：三种剔除方案的大乱斗

| 特性 | **PVS (预计算)** | **Software Occlusion (CPU软光栅)** | **Occlusion Query (GPU硬件查询)** |
| :--- | :--- | :--- | :--- |
| **核心逻辑** | 离线算好，运行时查表 | CPU 算个低配版深度图 | 问 GPU “你看见了吗” |
| **延迟** | 无 | 无 | **高 (1-3帧)** |
| **动态物体** | **不支持** | **支持** | **支持** |
| **CPU开销** | 极低 (查表) | **高 (软光栅化)** | 低 (发命令) |
| **GPU开销** | 无 | 无 | 低 (画包围盒) |
| **内存开销** | **高 (存数据)** | 低 (Z-Buffer) | 极低 |
| **适用场景** | 迷宫、室内、静态城市 | 动态战场、GPU瓶颈、现代PC/主机 | 镜头特效、不做精确剔除的大型物体 |

**Unity 的选择**：
*   Unity 默认只提供了 **PVS** (`Occlusion Culling` 面板)。
*   对于 **Lens Flare**，Unity 内部使用了 **Occlusion Query**。
*   如果你想要 GPU Query 做剔除，通常需要自己写 Shader 或者用 CommandBuffer，或者购买类似 `Perfect Culling` 这样的插件。
