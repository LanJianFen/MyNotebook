作为渲染工程师，当我们意识到“这只是个 1D 函数”时，我们的眼睛是会放光的。因为这意味着我们可以祭出图形学里最古老、也最强大的优化杀招：**查表（Look-Up Table, LUT）！**

### 工程师的极致压榨：从数学计算到 1D LUT

让我给你看看，你的这个认知，在真实的引擎底层是怎么被用来压榨 GPU 性能的：

**1. 之前的痛点：**
回忆一下我们那段 HG 公式的代码：
`return num / (12.56637 * pow(denom, 1.5));`
这里面有一个极其讨厌的指令：`pow(denom, 1.5)`。
在 Ray Marching 的 `for` 循环里，每一个像素要循环 64 次。如果屏幕是 4K 分辨率，这就意味着 GPU 每一帧要执行数千万次昂贵的幂运算（Transcendental Function）。对于老旧硬件或移动端，这会造成不小的负担。

**2. 你的顿悟带来的优化方案：**
既然它就是一个 1D 函数，我们为什么要在实时循环里死算呢？
*   **离线预计算：** 在游戏加载阶段，我们写个小脚本，把 $\cos\theta$ 从 -1 到 1 分成 256 份。计算出 256 个结果，存进一张长条形的、尺寸为 **256 x 1** 像素的一维纹理（1D Texture）里。
*   **实时白嫖：** 在 Ray Marching 循环里，公式被粗暴地替换成这样：
```glsl
// 1. 算点乘，范围是 [-1, 1]
float cosTheta = dot(L, V); 

// 2. 映射到纹理 UV 坐标 [0, 1] 范围内
float u = (cosTheta + 1.0) * 0.5; 

// 3. 采样那张 1D 贴图，直接得到结果！不消耗任何算力！
float phase = texture1D(PhaseLUT, u).r; 
```

### 进阶：云层渲染的绝杀武器

如果只是普通的 HG 函数，现代 GPU 的 ALU（算术逻辑单元）其实跑得飞快，算一下 `pow` 也抗得住，很多时候大家懒得去存一张贴图。

**但是！当你要渲染天空中的真实体积云时，你的这个 1D 认知就是救命稻草！**

真实云层的水滴散射根本不服从 HG 这么简单的公式，它服从物理上极其变态的 **Mie 散射（米氏散射）**。Mie 散射的解析解包含无穷级数的贝塞尔函数，在 Shader 里直接算是**绝对不可能**的，GPU 会当场爆炸。

但由于**云这种介质也是统一的**，所以 Mie 散射在同一种云里，**也是一个 1D 函数！**
所以，寒霜引擎、虚幻引擎在渲染云层时，都是用物理软件离线跑出 Mie 散射的 1D 曲线，把它存进一张 1D LUT（或者拟合在一张 2D LUT里供不同云层高度采样）。

在运行时，极其复杂的量子物理散射，被降维成了一次极其便宜的 `texture()` 纹理读取指令。
