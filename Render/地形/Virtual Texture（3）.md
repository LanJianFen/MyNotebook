页表为什么是一张特殊的贴图

这是一个非常好的“为什么”！

通常我们在编程时，存数据（比如数组、坐标）会用 **Buffer（缓冲区）** 或者 **Array（数组）**。
但在 VT 技术里，我们偏偏要用 **Texture（纹理）** 来存这本“电话簿（页表）”。

这主要有 **4 个硬核理由**，每一个都利用了显卡（GPU）的物理特性：

---

### 1. 只有纹理拥有“硬件级 Mipmap”

这是最致命的理由。

*   **如果用 Buffer/数组：**
    Buffer 是扁平的一维数据。它没有“层级”的概念。
    如果你想模拟 Mipmap，你必须自己写一套极其复杂的逻辑：
    `if (level == 0) index = ...; else if (level == 1) index = ...;`
    这在 Shader 里非常慢。

*   **如果用 Texture：**
    纹理天生就有 Mipmap 链。
    显卡硬件只需一条指令 `tex2Dlod`，就能**自动**帮你找到：“基于当前屏幕像素的远近，我应该去读页表的第几层？”
    这个计算过程是 GPU 的 **TMU (纹理映射单元)** 硬件免费送你的，不占 Shader 算力。

**结论：**
因为 VT 的页表结构必须和原始大图的 Mipmap 结构一一对应（大图缩一半，页表也要缩一半），所以只有纹理最合适。

---

### 2. 只有纹理支持“双线性插值的...反面”

这听起来有点绕。
普通的纹理，我们需要 Linear Filtering（让颜色平滑过渡）。

**但在页表纹理里，我们绝对禁止插值！**
*   **页表存的是：** “第 5 号格子”。
*   **如果不小心插值了：** 第 5 号和第 6 号插值，变成了 **5.5 号**。
*   **后果：** 你去物理图集的 5.5 位置采样，那里可能是两个材质的接缝，你会看到一条奇怪的黑线或乱码。

我们需要的是 **Point Sampling (最近邻采样)**。
纹理采样器（Sampler）允许我们把 Filter 设为 `Point`。这能保证：要么读到 5，要么读到 6，绝对不会读到 5.5。
虽然 Buffer 也能做到，但配合上一条 Mipmap 的需求，纹理依然是赢家。

---

### 3. GPU 的缓存机制 (Texture Cache Swizzling)

这是底层性能优化的关键。

*   **Buffer/数组的存储：**
    是线性的。`[0, 1, 2, 3, ...]`
*   **纹理的存储：**
    是 **Swizzled (Z-order 曲线)** 的。显卡存纹理时，不是一行一行存的，而是把相邻的 2x2 或 4x4 像素块挤在一起存。

**这对 VT 意味着什么？**
当你渲染屏幕上的一个像素时，你很可能马上就要渲染它旁边的像素。
因为纹理在显存里是块状存储的，旁边像素所需的页表数据，极有可能**已经在显卡的 L1/L2 Cache 里了**。
这就大大减少了显存带宽压力。

---

### 4. 数据格式的完美契合

页表需要存什么信息？通常是这 4 个数：
1.  **PageX:** 物理图集里的 X 坐标。
2.  **PageY:** 物理图集里的 Y 坐标。
3.  **Scale:** 缩放级别。
4.  **Meta:** 比如“是否加载完成”、“各向异性过滤参数”等。

这刚好对应纹理的 **RGBA 四个通道**！
我们可以用一张 `R16G16B16A16_UINT`（无符号整数）或者 `R8G8B8A8_UNORM` 的贴图，完美塞入这些数据。

---

### 总结：它是一张“Excel 表格”

所以，虽然它叫“Indirection Texture（间接纹理）”，但在 Shader 程序员眼里：

它是**披着纹理外衣的“二维 Excel 表格”**。

*   它**不给人看**（看起来是红红绿绿的马赛克）。
*   它**给 GPU 看**。
*   它利用了 GPU 对纹理的一切硬件加速（Mipmap 选择、缓存局部性、自动 UV 归一化），来实现极其高效的查表操作。
