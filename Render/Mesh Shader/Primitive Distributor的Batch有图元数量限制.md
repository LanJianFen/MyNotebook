

这个问题问到了芯片设计的“七寸”。

为什么图元数量（比如每个 Batch 或 Meshlet 里的三角形数）要有严格的上限限制？并且这个数字通常被巧妙地设定在 **64、128 或 256** 这样特定的数字？

在 GPU 底层微架构设计中，**没有什么是无限的，因为物理硅片的面积和导线是“寸土寸金”的**。图元数量被严厉限制，主要由以下 4 个最核心的硬件和调度原因决定：

---

### 原因一：片上静态内存（SRAM）的物理造价极度昂贵

我们之前提到，PD 把 Batch 打包发给 GPC 后，GPC 算完顶点，需要把结果存起来，这就需要用到**片上缓存**。

*   **海量属性数据的压力：** 算完的顶点不仅有 `XYZW`（位置），还有法线、切线、好几套 UV，甚至顶点色等大量属性（Attributes）。一个处理后的顶点体积可能高达上百个字节。
*   **硬件参数缓存（Parameter Cache）：** 在 Vertex Shader 算完，但 Rasterizer（光栅化）还没有开始画像素之前，这些数据必须暂存在 SM 内部一块叫 Parameter Cache 或 Attribute Ring 的极高速 SRAM 存储器里。
*   **为什么不能放几千个图元？** SRAM 在芯片上占用的物理面积是非常庞大的（你可以看显卡 Die 的显微摄影图，大片大片都是缓存）。如果一个 Batch 允许有 1000 个图元，那每个执行单元都需要配备 MB 级别的专属高速缓存来“憋着”这些中间数据。这会导致整块芯片的成本飙升，晶体管发热爆炸，这是物理上绝对不可接受的。因此，**硬件工程师通过精密计算，得出 64 或 128 个图元的缓存量，是性能和芯片面积之间的“甜点（Sweet Spot）”。**

### 原因二：为了迎合 GPU 的“魔法数字” —— Warp/Wavefront

你可能注意到了，限制数字通常是 64 或 128，为什么不是限制在 100 或 73 呢？这跟 GPU 处理数据的底层执行单元强相关。

*   **SIMT 并行魔法：** 现代 GPU 并非一个线程一个线程单干的。NVIDIA 的 GPU 会把 **32 个线程** 绑在一起（这叫一个 **Warp**），AMD 则是 **64 个线程** 绑在一起（叫 **Wavefront**）。这些线程执行同样的指令，这就是 SIMT（单指令多线程）。
*   **完美的对齐映射：** 当一个包含 **64 个图元** 的 Batch 送到 SM 时，调度器怎么干活最爽？
    *   如果是发给图元装配阶段，刚好分配 **2 个 Warp （32 x 2 = 64）**。
    *   如果是发给光栅化阶段做三角形遍历，也是分配完美的整数个 Warp 去并行计算边缘方程。
*   如果图元数量不设限，或者是个奇葩数字，就会导致某些 Warp 被拆散，有大量 ALU（算数逻辑单元）空跑，造成极大的算力浪费。

### 原因三：保持流水线如“细水长流”，掩盖延迟

GPU 的威力在于它是一根超长、超宽的**流水线（Pipeline）**。流水线最怕的事情就是“某一个车间突然卡了很久，导致后面全部停工待料”。

*   如果图元数量不限制，假设 PD 允许把 5 万个三角形打死包成一个巨型 Batch 塞给某个多核单元。
*   这就像流水线上突然滚来一个巨大的铁疙瘩，这个单元可能要花好几个毫秒都在埋头苦啃这 5 万个三角形的位置信息。
*   此时，它后方的“光栅化器”和“像素着色器”会因为迟迟拿不到这批图元的位置信息，全部处于饥饿（Starvation）状态，白白浪费电。
*   **切成小块（64个）的智慧：** 把大的模型切成一连串 64 个图元的 Batch。GPC-A 的顶点单元花极短的时间（几十纳秒）算完这批顶点，立刻扔给后面的光栅化器。然后它马上回头去接下一个 Batch。这样，**整个显卡从最前面的读取，到最后面的涂色，都在像涓涓细流一样同时满载运转，互相掩盖了延迟。**

### 原因四：交叉路由（Crossbar）的带宽防爆机制

在早期对话里我们聊过，算完之后，不同 GPC 会通过内部十字交叉总线（Crossbar）把三角形抛给对应负责该屏幕区域的光栅化器。

*   跨区域搬运数据是一个**极其消耗芯片内部总线带宽**的操作。
*   如果一个 Batch 特别极大（比如包含了横穿整个屏幕的几千个三角形），当它出炉的瞬间，会在内部总线上产生巨大的**突发性数据海啸（Burst Traffic）**，堵死其他所有正在通讯的数据报文。
*   限制每个包的图元上限，实际上也就是在**限制每次系统内部物流的最大包裹体积**，从而避免内部总线的网络拥堵宕机。

---

### 终局演进：这也是 Mesh Shader 的设计边界

这就是为什么，当图形管线迎来了革命性的 **Mesh Shader** 时，虽然我们摆脱了前端固件 PD 的束缚，但微软 DirectX 和 GPU 厂商依然在 API 层面设置了极为严苛的数量限制。

在写 Mesh Shader 代码时，你必须在 Shader 头部声明：
`[outputtopology("triangle")]`
`[numthreads(128, 1, 1)]`  <-- 对应 Warp 的倍数
**且输出的顶点数最大只能是 256，输出的图元数最大只能是 256（老一点的硬件甚至只建议 64 和 128）。**

因为硬件的物理定律没有变。无论是固件 PD 自己切分，还是咱们程序员用 Mesh Shader 提前切分，**“利用小块局部 SRAM、迎合 SIMD 线程组并发、如细水一般润滑整条流水线”**，这就是 GPU 微架构永恒不变的三大黄金定律。
