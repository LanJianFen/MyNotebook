

这是一个极度硬核且非常内行的微架构问题！

Primitive Distributor（PD）在切分 Batch 时，并不是简单地写一个 `if (count == 100) { 打包 }` 的逻辑。实际上，PD 拥有一套复杂且实时的**硬件启发式规则（Heuristic Rules）**。

判定一个 Batch 装满并将其“封箱发货”（发给某个 GPC）的条件，是基于**“触发器机制（OR 逻辑）”**的：只要触碰到了以下 **三个核心限制** 中的任何一个，PD 就会立刻斩断当前网格，强行结束打包。

让我们像设计这块硅片的芯片工程师一样，来看看这三个“红线”到底是什么：

---

### 红线一：图元数量上限（容量红线）
这是最直观的一个物理限制。PD 内部的硬件缓冲区（FIFO buffer）大小是固定的。

*   **硬件死线：** 根据不同的 GPU 架构代数，一个 Batch 最多只能容纳固定数量的图元（三角形、线段、点），比如典型的数字是 **64 组** 或 **128 组** 索引。
*   **判断过程：** PD 内部有一个计数器。当 IA（输入装配器）源源不断送入装配好的三角形索引时，`Primitive_Count++`。一旦此数字达到硬件设定的最大阈值，无论别的情况如何，这个 Batch 都会被认定为“装满了”。

### 红线二：独立顶点缓存上限（💥最核心、最复杂的红线）
如果只看图元数量，那设计芯片就太简单了。**PD 切分 Batch 的最大难点和真正瓶颈，在于监控“独立顶点数”。**

回忆一下上一回合我们提到的：GPC 内部有一个专属的、不与其他工厂共享的“处理后顶点缓存（PTVC, Post-Transform Vertex Cache）”。
这个 PTVC 的容量非常小（通常只能存几十个计算好坐标的顶点，比如 32 个或 64 个）。

*   **硬件死线：** PD 必须保证，它发往 GPC 的这个 Batch，**其引用的“不重复顶点数（Unique Vertices）”，绝对不能超过 GPC 里的存量上限！**
*   **判断过程：**
    PD 在扫描 Index Buffer 时，不仅在数三角形，还在**实时维护一张“唯一索引比对表”**。
    假设硬件 PTVC 容量是 32 个顶点：
    1.  读入三角形1（索引 0, 1, 2）：发现 3 个新顶点。当前 `Unique_Vertex_Count = 3`。
    2.  读入三角形2（索引 1, 2, 3）：发现 1 和 2 是老朋友。只有 3 是新顶点。当前 `Unique_Vertex_Count = 4`。
    3.  ……继续狂扫……
    4.  读入第 N 个三角形（索引 99, 100, 101）：全是新顶点。PD 一算，糟糕，加上这 3 个，当前 Batch 包含的独立顶点数量就达到 **33 个**了！
    5.  **立刻触发熔断：** 哪怕此时图元计数器才累加到倒数第 20 个三角形（容量红线没满），**PD 也会毫不犹豫地强行切断！** 把前 N-1 个三角形封箱发走。

**为什么要这么狠？**
因为如果不切断，把包含 33 个独立顶点的包发给 GPC，GPC 内部容量为 32 的缓存就会发生**“缓存溢出（Cache Eviction/Thrashing）”**，导致原本可以复用的顶点被挤出内存，造成灾难性的重复计算。

### 红线三：状态或数据流中断（逻辑红线）
即便容量没满、顶点上限没触及，某些来自上游软件（API）的改变，也会强制 PD 立刻清空并发出当前的 Batch（专业术语叫 **Flush**）。

*   **Draw Call 结束：** 一次 `DrawIndexed` 调用结束了。前一个模型的剩余几十个三角形不能和下一个模型的三角形混包。因为它们的顶点数据源（Vertex Buffer）和变换矩阵都不一样了。所以必须 Flush。
*   **拓扑改变（Topology Change）：** 如果游戏引擎前一秒在画 Triangle List，下一秒突然切换画 Triangle Strip。组织规则变了，当前 Batch 必须强行封死发出。

### 打一个形象的比喻

你可以把 PD 想象成一个**“大巴车调度员”**。
大巴车（发往GPC的Batch）有两项硬性规定：
1.  **红线一（座位数限制）：** 最多只能坐 64 个人（64个图元）。
2.  **红线二（行李厢限制）：** 如果这批乘客带了特别多**不同的行李箱**（独立顶点），导致大巴下面 32 个格子的行李厢塞满了。
3.  **调度规则：** 就算座位才坐了 20 个人，只要行李厢满了，调度员也会吹哨子：“不准上了！马上发车！”

高精细扫描模型（如 500 万面乱糟糟的网格）的问题就在于：**它的索引极其分散！乘客们彼此不认识，每个人都带了奇形怪状的行李（几乎没有共享顶点）。**
导致大巴车常常只坐五六个人，行李厢就爆了，只能空荡荡地发车。这使得后端的 GPC 算力（大功率发动机）一直跑空载，效率极速下滑。

### 结语与现代管线的交汇点

如果你理解了上述过程，你就会对今天火热的 **Mesh Shader (网格着色器)** 产生更深层的敬畏：

为什么微软 DX12 Ultimate 和 NVIDIA 强烈推荐 Mesh Shader？
因为 Mesh Shader 强制要求我们在**资产离线烘焙阶段（或者在软件预处理阶段）**，**用 CPU 或 Compute 算法，把那个庞大的模型，极尽完美地切分成一个个“不超过 64 个图元，且不包含超过 64 个独立顶点”的网格簇（Meshlets）！**

**Meshlet 的本质，就是程序员帮愚蠢的硬件 PD 提前做好了最完美的打包工作！** 在运行时，硬件可以直接按照编排好的逻辑丢给 SM 执行，彻底淘汰了 PD 那一套性能低下的实时动态判定机制。
