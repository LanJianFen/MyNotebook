

为了把这个问题讲透彻，我们需要把显微镜对准 **Input Assembler (IA，输入装配器)** 和 **Primitive Distributor (PD，图元分发器)** 之间的这道微观工序。

在硬件设计上，处理 Index Buffer 主要是 IA 的工作，但 **PD 必须基于 IA 吐出的 Index 数据来构建分发策略**。这两者通常在硬件前端（Front-End）是极其紧密耦合的。

让我们以一次普通的 `DrawIndexed` 调用为例，详细推演在面对 Index Buffer 时，PD 到底做了什么。

---

### 第一步：从“原始索引”到“逻辑图元”（IA的作用，PD的前置条件）

当 GPU 开始执行 `DrawIndexed` 时，最先读取显存（Index Buffer）的是 IA。
假设你提交的是一个 `TriangleList`，Index Buffer 的内容是：`[0, 1, 2,  1, 3, 2,  ...]`。

1.  **IA 获取数据：** IA 从内存中读取这些纯粹的数字（通常是 16位或32位整数）。
2.  **拓扑组装（Topology Assembly）：** IA 根据拓扑状态，把这些分散的数字按组打包。
    *   图元 0：索引 `(0, 1, 2)`
    *   图元 1：索引 `(1, 3, 2)`
3.  **移交 PD：** IA 不做顶点计算（它不去拿顶点的 XYZ 位置），它只是把**“由索引号组成的逻辑三角形”**推入一个硬件 FIFO（先进先出缓存），交由 PD 处理。

---

### 第二步：PD 的核心操作——“批处理与边界切割”（💥最硬核的部分）

此时，PD 面对的是源源不断的“索引组”流。如果按照简单的“轮询（Round-Robin）”算法，PD 把图元 0 发给 GPC-A，把图元 1 发给 GPC-B，会发生什么灾难？

**灾难：Vertex Cache（顶点缓存）命中率暴跌！**
*   这正是 Index Buffer 发明出来的初衷：**共享顶点，减少 Vertex Shader (VS) 的重复执行**。在上例中，顶点 `1` 和 `2` 是被两个三角形共享的。
*   如果图元 0 和图元 1 **都在同一个 GPC** 里执行，GPC 内部的 **Post-Transform Vertex Cache (PTVC，变换后顶点缓存)** 会记住顶点 `1` 和 `2` 计算后的 `gl_Position`。算第二个三角形时，可以直接复用，VS 只需要算顶点 `3`。
*   如果 PD 把图元 0 发给 GPC-A，图元 1 发给 GPC-B。由于 GPC 之间的缓存**不共享**，GPC-A 会算一遍顶点 1、2，GPC-B 也会重新算一遍顶点 1、2。**共享顶点的优势荡然无存！**

**👉 所以，PD 在这里必须做一件极其复杂的事情：有局部空间意识的批处理（Batching / Chunking）！**

1.  **聚集（Accumulation）：** PD 不会来一个三角形就发一个。它会把相邻的几十个逻辑三角形（比如 64 个）聚集在一个称之为 **Batch（批次）** 或 **Patch** 的容器里。
2.  **分析 Index 连接性（部分架构）：** 优秀的 PD 硬件逻辑会尽量保证同一个 Batch 内的三角形有着大量连续、重复的 Index。
3.  **打包分发：** PD 将一整个 Batch 作为一个完整的不可分割的任务，发送给某一个 GPC。在这个 GPC 内部，由于三角形们呆在一起，它们的共享顶点可以达到极高的 PTVC 命中率。
4.  **承受“边界代价”：** 当 Batch 被填满，PD 必须切断当前的连通网格，开启下一个 Batch 发给另一个 GPC。**在两个 Batch 的缝隙处（即被切割的边缘），那些理论上共享的顶点必定会被重复计算（Duplicated Vertex Shading）。** 这是为了宏观并行负载均衡，必须付出的微观代价。

---

### 第三步：生成“发货单”与打标签（Tagging）

当 PD 决定把包含 64 个“由 Index 组成的逻辑三角形”的 Batch-0 发给 GPC-A 时，它还要在数据包上附带额外的信息：

1.  **顺序序列号（Sequence ID）：**
    PD 会给 Batch-0 打上 `SEQ_001`，给发往 GPC-B 的 Batch-1 打上 `SEQ_002`。如之前所述，VS 算完之后，后端的 Crossbar 必须根据这个标签重新排队，保证光栅化顺序不变。
2.  **引用的顶点地址区间（Vertex Fetch Info）：**
    PD 只下发了 Index。真正的顶点数据（位置、法线、UV）还在 Vertex Buffer 里。PD 会告诉 GPC-A 的线程调度器：“你需要根据这些 Index，去启动相应的 Fetch 线程，从 Vertex Buffer 里把真正的几何数据捞出来，喂给 Vertex Shader。”

---

### 为什么在面对海量高精细网格时，PD 在这里“挂”了？

现在你知道了上面这套极其复杂的“读取->拓扑组装->分析缓存连通性->打批次->分发->打标签”的硬件逻辑。

想象一下你导入了一个 500万面 的高精细雕刻模型：
1.  **极度离散的 Index：** 模型非常密集，相邻三角形常常横跨大量的顶点，Index Cache 命中率下降，PD 在构建高内聚 Batch 时效率变低。
2.  **吞吐量极限：** PD 是一个位于芯片中央的固定硬件单元。假设它的硅片面积决定了它每个时钟周期最多只能处理和分发 4 个三角形（例如基于老架构的预估）。如果在 2GHz 频率下，它每秒绝对能处理的图元量被物理锁死在了 80亿 个。
3.  **后端饿死：** 后端有 80 个流式多处理器（SM）正在嗷嗷待哺。每个 SM 一瞬能算大量顶点，但前端的 PD 被海量的极小三角形塞爆了计算分发逻辑，处理不过来。这就是经典的 **Frontend Geometry Bound**。

### 总结

面对 Index Buffer，PD 扮演的是一个**“带有缓存保护意识的物流打包站”**：
它不但要负责把线性堆叠的索引号打包成“批次”发给并行的工厂（GPC），**还要绞尽脑汁地保证把具有公共索引号（共享顶点）的三角形尽量塞进同一个包裹里**，从而拯救后端的顶点着色器缓存。

这也是为什么在传统管线时代，经常会有诸如 "Forsyth algorithm" 或者 "AMD Tootle" 这样的工具，在离线阶段对 Mesh 的 Index Buffer 进行重新排序优化——本质上就是**在软件层面上帮 PD 减轻“打包”和“维持顶点缓存命中率”的压力**。而到了 Mesh Shader 时代，这个复杂的“动态打包分析”过程被完全抛弃，取而代之的是在烘焙阶段直接静态切分好的 Meshlets。
