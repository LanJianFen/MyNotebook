

啊，我完全明白你的意思了！你问到了延迟渲染性能优化的**最绝对的核心**。

如果一盏灯对所有像素都叠加一次计算，那就是 $O(ScreenPixels \times Lights)$。如果场景里有 1000 盏路灯，每帧跑 1000 次全屏计算，哪怕是最顶级的 RTX 4090 也会瞬间冒烟。

所以，**怎么让光源精确定位到它究竟照亮了哪些像素，从而跳过无用的计算？** 

在渲染工程的演进历史中，我们通过**三种不同时代的算法/架构**来解决这个问题。作为喜欢算法的工程师，我们来一步步看它是怎么做到“精准打击”的：

---

### 第一代解法：利用光栅化硬件的“光照体积法” (Light Volumes)
**核心思想：把“寻找被照亮像素”的问题，转化为“渲染几何体”的问题。**

这也是最经典的做法。我们怎么知道一个点光源（球形衰减）照亮了谁？
答案是：**我们直接在场景里画一个球！**

1. **确定范围：** 这个球（Sphere Mesh）的半径，严格等于这个点光源的衰减最大半径。超出这个球，光照贡献为 0。
2. **硬件光栅化：** 我们把这个球丢给显卡渲染。GPU 的光栅化器（Rasterizer）非常聪明，它会计算出这个 3D 球体**在屏幕上覆盖了哪些 2D 像素**。只有球覆盖的像素，Fragment Shader 才会被触发去读 G-Buffer 算光照！
3. **软件算法之美（模板剔除 Stencil Culling）：**
   光画个球还不够，如果物体离得很远，球其实根本没碰到它（比如球在镜头前，物体在 1000 米外）。
   为了连这些像素也跳过，我们用一种极其巧妙的**两遍深度测试（Depth Test）算法**：
   * **Pass 1：** 先渲染球的**背面（Backface）**。如果球的背面被场景物体遮挡了（Depth fail），说明物体在这个球的前面或里面，我们在 Stencil Buffer 里把该像素标记为 `1`。
   * **Pass 2：** 再渲染球的**正面（Frontface）**。只有当正面没有被遮挡（它在物体前面），并且 Stencil 为 `1` 的像素，才真正调用光照计算。
   
   **结果：** 经过这套组合拳，光源就只会在**“它衰减半径范围内，且真正包裹住几何体”**的那极其有限的几个像素上执行叠加计算。

### 第二代解法：纯软件计算的“分块延迟计算” (Tiled Deferred Shading)
**核心思想：抛弃画球，把屏幕切成网格，提前算好每个网格里有哪些灯。**

画几千个球（Draw Call）仍然很费 CPU，并且过度重绘（Overdraw）严重。现代引擎（比如虚幻4早期、寒霜）改用 **Compute Shader** 纯软件算法来解决。

1. **切分屏幕：** 我们在软件层面，把 1080p 的屏幕切成一个个 $16 \times 16$ 像素的小方块（Tile）。
2. **构建 3D 视锥体：** 在 Compute Shader 里，读取这个 Tile 内 256 个像素的 G-Buffer 深度。找到这个 Tile 最浅的深度（MinZ）和最深的深度（MaxZ）。利用屏幕坐标和 MinZ/MaxZ，我们就为这个方块构建出了一个**受限制的三维视锥截面（Frustum AABB）**。
3. **碰撞检测求列表 (Light Culling)：** 
   接下来是纯数学计算：遍历场景里 1000 盏灯，分别用这 1000 个灯的包围球，去和这个 Tile 的 3D 视锥体做**相交测试求交集（Intersection Test）**。
   如果灯的球体碰到了这个 Tile 的 3D 空间，就把这盏灯的 ID 写进一个列表里，存入 GPU 的高速共享内存（Shared Memory）。
4. **像素光照计算：**
   终于到了算光照的时候！Tile 里的任何一个像素，**它根本不需要管这 1000 个灯，它只需要读取刚才算出来的、属于自己这个 Tile 的小列表**（可能只有 3 盏灯）。然后只叠加这 3 盏灯的影响。

### 第三代（当前最强）：分簇延迟渲染 (Clustered Deferred Shading)
**核心思想：既然二维切分不完美，那我们把整个相机的 3D 视锥体切成一个个立体的格子（体素化）。**

Tiled/分块算法有个致命弱点：如果一个 Tile 里，有个像素在鼻子尖前 1 米，另一个像素在 1000 米外远景（比如建筑边缘），这个 Tile 的 MinZ 和 MaxZ 跨度极大，拉出的 3D 空间极其狭长。很多其实照不到前排物体的灯也会被算进来。

《毁灭战士》(DOOM 2016) 引领了现在的行业标杆算法——**Clustered Shading**：

1. **3D 空间分簇：** 不仅在屏幕 XY 轴上切网格（比如 16x16），还在深度 Z 轴上切片（通常是按对数切 24 或 32 片）。整个相机的视野被切成了比如 $16 \times 16 \times 32 = 8192$ 个 3D 小房间（Cluster）。
2. **灯光分发算法：**
   在渲染物体之前！先开一个 Compute Shader，把场景里的 1000 盏灯投射到这 8192 个小房间里。算出每个小房间里具体有哪些灯（依然是做相交测试求列表）。生成一个巨大的 3D 查找表（Look-Up Table）。
3. **像素反查列表：**
   到了最后光照计算的阶段。每个像素（Fragment）只需做这几件事：
   * 读自己的世界坐标/深度。
   * 算一下自己的坐标究竟落在了那 8192 个小房间的 **哪一个** 里？（`Index = fn(x, y, z)` 的纯数学映射）。
   * 根据 Index 去查那张表，拿到自己这个小房间的专属灯光列表。
   * 循环这个列表算光照。

### 总结回答你的疑问：

光源并不知道自己照亮了谁，像素也不知道自己受谁影响。
为了连接它们：
在过去，我们用**画 3D 范围球 + 硬件深度测试**的硬件过滤机制来让像素“被动”接受它范围内的光。
在现在，我们用**软件层面的 3D 空间分区数据结构（Tile/Cluster）和相交算法**，让像素“主动”去极小的范围里去查有哪些光离自己近。

所以绝大多数像素，在光照 Pass 里只会发生 1 到 5 次光照计算，这是现代游戏能同屏成百上千光源且保持 60 帧的根本原因！
