### 1. 离线烘焙的“撒谎”阶段：强行对称

先证明一下你的结论 $V = N = R$。
反射向量的计算公式是：$R = 2(V \cdot N)N - V$。
如果我们强制规定玩家正对着法线看（即 $V = N$），代入公式：
$R = 2(N \cdot N)N - N$
因为 $N$ 是单位向量，所以 $N \cdot N = 1$。
$R = 2N - N = N$ 

**结果真的是 $R = V = N$！**

**这个假设在物理上意味着什么？**
它意味着在预计算的时候，我们**强行规定：所有的光线反射（BRDF 形状），必须完美地、对称地围绕着法线 $N$ 散开！**
因为你正对着物体看，高光的中心点就在正中央，它不会因为透视或者掠射角产生任何的“拉伸”或“倾斜”。

如果把 BRDF 想象成一个水滴形的反射波瓣（Lobe）：
*   **真实的物理：** 如果你从侧面看（掠射角），这个水滴会被严重拉长，指向真实的反射方向 $R$。
*   **Epic 的假设：** 无论什么情况，我全把它当成一个正立的、完美圆润的“胖水滴”，永远笔直地站在法线 $N$ 上（因为此时 $R=N$）。

因为这个“胖水滴”是绝对旋转对称的，我们才能够顺理成章地用它作为核（Kernel），去对周围的天空盒进行全向模糊（卷积），并把结果存进 Mipmap 里。

### 2. 实时渲染的“圆谎”阶段：移花接木

如果我们在实时渲染（打游戏）的时候，也坚持这个假设，那就完了——所有的环境反射高光都会永远出现在物体的正中心，永远跟着法线走，那画面看起来就像贴了一张死板的贴图。

**所以，在写 Fragment Shader 时，Epic 翻脸不认人了！**

实时 Shader 代码是这样的：
```glsl
// 1. 获取真实的法线 N 和 真实的视线 V（绝对不是 V=N）
vec3 N = normalize(Normal);
vec3 V = normalize(CameraPos - WorldPos);

// 2. 算出一个真实的、偏向一侧的反射向量 R
vec3 R = reflect(-V, N);

// 3. 移花接木开始！
// 我们拿着这个真实的、倾斜的 R，去采样那张用“绝对正立 (V=N)”假设烘焙出来的 Cubemap
vec3 prefilteredColor = textureLod(prefilterMap, R, lod).rgb; 
```

**看出这个极其狡猾的操作了吗？**

Epic 在烘焙的时候，假装视线就在法线上（$V=N=R$），烤出了一堆**完美对称的模糊光斑**。
但在实时运行的时候，它计算出**真实的反射方向 $R$**，然后顺着这个 $R$ 去贴图里“抓取”那团完美对称的光斑，强行贴在现在的反射方向上！

---

### 3. 这个“谎言”的代价是什么？

因为你拿着“正对着看（$V=N$）”算出来的模糊形状，去代替“从侧面看”的模糊形状，必然会产生物理上的破绽。

**视觉代价：掠射角反射拉伸的丢失（Missing Grazing Angle Elongation）。**
在真实的物理世界中（或者你用离线渲染器如 Arnold、Blender Cycles），当你视线几乎平行于一个粗糙的桌面看过去时（也就是 $V$ 和 $N$ 夹角接近 90 度），由于 BRDF 的微面元遮挡效应，桌面的高光反射会被**沿着视线方向严重拉长**（就像你在雨夜看马路上的车灯，反光是一条长长的线）。

但是，在使用了 Split-Sum 假设的现代游戏引擎里，因为烘焙时强行用了 $V=N$ 的对称假设，游戏里的马路反光（只靠 IBL 的部分）永远是一坨圆乎乎的光晕，**它不会拉长**！

为了弥补这个由 $V=N$ 带来的史诗级破绽，后来的图形学大佬们只能在实时阶段打各种补丁：
1. **各向异性过滤（Anisotropic IBL）**：极其昂贵。
2. **屏幕空间反射（SSR）**：在屏幕空间做真实的射线步进，因为有真实的 $V$，所以 SSR 能完美呈现拉长的反射线。这也是为什么开启 SSR 后，雨天地面的反光瞬间变真实了。
