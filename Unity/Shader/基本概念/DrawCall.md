

你问到**Draw Call**，这可以说是整个游戏渲染性能优化里**最臭名昭著、也最核心的“大Boss”**。

前面我们聊了 `CBUFFER`（打包数据）和 `SRP Batcher`（批量发车），它们最终要解决的终极问题，其实都是为了**拯救因为 Draw Call 过多而崩溃的 CPU**。

为了让你彻底看透 Draw Call，我们继续用**“包工头（CPU）与超级画刷（GPU）”**的比喻来把底层逻辑扒个精光。

---

### 一、 什么是 Draw Call？（一句话定义）

**Draw Call，就是 CPU（主板处理器）向 GPU（显卡）发送的一条命令：“喂！用当前的设置，给我把这个模型画出来！”**

听起来很简单对吧？但为什么游戏开发里天天喊着要“降低 Draw Call”呢？

### 二、 核心误区：Draw Call 卡，并不是因为“画画”慢！

很多新手以为，Draw Call 多导致游戏卡，是因为 GPU 画不完。**大错特错！**
GPU 是一个并行计算的怪物，你让它一次性画 1 万个面的怪兽，它眼都不眨瞬间画完。

真正慢的，是 CPU 在喊出那句“给我画”**之前**，所必须做的**“准备工作（改变渲染状态 SetPass Call）”**。

**【生动的比喻】：**
*   **CPU（包工头）：** 智商极高，但做事极其繁琐守规矩。
*   **GPU（瞎子画师）：** 没有脑子，看不见全局，但只要你把笔和纸塞到他手里，他画画速度是光速。

现在要画 100 个不同颜色的小兵。

**在没有优化的状态下，CPU 的工作流是这样的（产生 100 个极重的 Draw Call）：**
1.  CPU 找出一张红色的纸（绑定纹理）。
2.  CPU 找出一根粗画笔（绑定 Shader）。
3.  CPU 找出红色的颜料（绑定材质参数）。
4.  CPU 告诉画师：“不要画出画布外哦”（设置深度测试、裁剪状态）。
5.  **CPU 大喊一声：“Draw！（Draw Call）”** -> *画师 0.0001 秒画完。*
6.  CPU 把刚才的红纸、画笔全部收起来。
7.  CPU 重新拿出一张蓝色的纸、一根细画笔、蓝色颜料……
8.  **CPU 再次大喊：“Draw！（Draw Call）”** -> *画师 0.0001 秒画完。*

**看出来了吗？** 画师（GPU）大部分时间都在**发呆**！他每次只花 0.0001 秒画画，却要等包工头（CPU）花 10 秒钟去疯狂切换纸和笔（这叫 **Render State Change 渲染状态切换**）。
当场景里有 2000 个物体时，CPU 就会因为不断地切换状态、发送 Draw Call 而彻底累死（CPU 满载），导致游戏掉帧。

---

### 三、 经典的 Draw Call 优化手段（怎么救 CPU？）

既然痛点在于“频繁切换状态和下达指令”，我们在游戏开发中常用的技术，其实就是**想方设法让 CPU 少说话**。

#### 1. 静态合批（Static Batching）- “把东西粘在一起画”
*   **做法：** 场景里有 100 块一模一样的石头。我们在 Unity 里勾选 `Static`。
*   **底层行为：** 游戏打包时，引擎直接把这 100 块石头的网格（Mesh）在内存里缝合成一个巨大的超级网格。
*   **结果：** CPU 只需要设置 1 次状态，发出 **1 个 Draw Call**：“把这个超级大石头给我画了！”Draw Call 直接从 100 降到 1。

#### 2. GPU 实例化（GPU Instancing）- “草丛与树林克星”
*   **做法：** 场景里有 1 万棵草。
*   **底层行为：** CPU 不再一个一个发命令，而是直接给 GPU 发送一个草的模型，以及一个包含 1 万个坐标位置的数组。
*   **结果：** CPU 发出 **1 个特权 Draw Call**：“用这个草的模型，在这个数组的 1 万个位置上，给我各画一棵！”（Draw Call 降为 1）。

#### 3. SRP Batcher（现代核心黑科技）- “轻量化发车”
这就是我们上一轮聊的结合了 `CBUFFER` 的技术！这里要纠正一个很多人都会犯的**高阶概念错误**：

**⚠️ SRP Batcher 其实并没有真正减少 Draw Call 的绝对数量，它减少的是“繁重的准备工作（SetPass Call）”！**

*   **底层行为：** 100 个小兵，材质全不一样，静态合批合不了。但是因为它们用了**同一个 Shader**，且变量都在 `CBUFFER` 里。
*   **CPU 的骚操作：** CPU 只需要在第一步，把画笔（Shader）设置好。接下来的 100 次 Draw Call，CPU **绝对不去切换画笔和渲染状态**。它只是飞速地指着内存里预先准备好的 CBUFFER 盒子喊：“画1号！画2号！画3号！”
*   **结果：** 依然有 100 个 Draw Call，但这 100 个 Draw Call 变成了**极轻量级的命令**，CPU 几乎没有开销，性能依然好到飞起。

---

### 四、 总结：一句话梳理它们的关系

1.  **Draw Call** 是导致游戏卡顿的万恶之源，本质是 CPU 为了画图而不断切换状态（换笔换纸）把自己累死。
2.  为了打败这个恶源，我们需要把零散的变量塞进 **CBUFFER（集装箱）** 规范化。
3.  因为有了规范化的集装箱，Unity 就能开启 **SRP Batcher**。
4.  开启了 SRP Batcher 之后，虽然 **Draw Call** 的命令还在发，但 CPU 彻底省去了“换笔换纸”的繁琐步骤，整个游戏的渲染性能瞬间起飞！
