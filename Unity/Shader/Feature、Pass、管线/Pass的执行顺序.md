

这是一个极其容易让人产生错觉的陷阱！

很多新手在写 Shader 时，会理所当然地认为：“Shader 从上往下写，那多个 Pass 肯定是从上往下依次执行的呀。”

**错！大错特错！**

真实的情况是：**多个 Pass 的执行顺序，绝大多数情况下根本不取决于你在代码里先写了谁、后写了谁，而是完全由渲染管线（C# 端）和 `LightMode` 决定的。**

只有在一种特定的“自定义特效”情况下，它们才会严格按照从上到下的顺序执行。

我们继续用上一问的“车间主任”打比方，把执行顺序分为以下三种核心情况：

---

### 情况一：不同 `LightMode` 的 Pass（完全由“车间主任”决定）

如果你的 Shader 里有多个 Pass，且它们的 `LightMode` 不一样。那么它们在代码里的上下顺序**毫无意义**。

在 URP 一帧的渲染画面中，管线有着极其严格的流程（Render Loop）。
假设你的 Shader 是这样的结构：
```shader
Pass { Tags { "LightMode" = "UniversalForward" } } // 代码排第 1
Pass { Tags { "LightMode" = "ShadowCaster" } }     // 代码排第 2
Pass { Tags { "LightMode" = "DepthOnly" } }        // 代码排第 3
```

实际执行时，主摄像机会这样安排工作：
1. **第一阶段（画阴影贴图）**：主任查户口，把所有 `ShadowCaster` 拉出来跑一遍（此时跑的是你**排第 2** 的代码）。
2. **第二阶段（画深度预渲）**：主任查户口，把所有 `DepthOnly` 拉出来跑一遍（此时跑的是你**排第 3** 的代码）。
3. **第三阶段（画正式彩色）**：主任查户口，终于轮到核心的 `UniversalForward` 跑了（此时跑的才是你**排第 1** 的代码）。

**结论：各司其职的 Pass，什么时候执行取决于当前渲染到了哪一步。**

---

### 情况二：相同 `LightMode`（或无 `LightMode`）实现多遍叠加（严格从上到下）

什么时候会“从上到下执行”？
当你为了做一个特效，**强行让同一个物体被画两遍及以上**，而且这两个 Pass 在同一渲染阶段被调用时。

最经典的例子：**传统二次元描边（Outline）**。
你需要一个 Pass 画比模型大一圈的黑色外壳，另一个 Pass 画正常的身体颜色。

```shader
// Pass 1：画黑色描边
Pass 
{
    Name "Outline"
    Cull Front // 剔除正面，只画背面
    // 把顶点沿着法线往外挤压一点点
    // 涂成纯黑色
}

// Pass 2：画正常身体
Pass 
{
    Name "Body"
    Cull Back // 正常画正面
    // 计算光照输出颜色
}
```
因为这两个 Pass 都没有写特殊的 `LightMode`（默认在同一阶段被当成普通物体渲染），此时 Unity 就会**严格按照你代码的书写顺序**：先跑 Pass 1 渲染一圈黑色的背面放进屏幕，再跑 Pass 2 渲染身体盖在黑色背面上。

如果你把这俩 Pass 换个位置，先画身体，再画膨胀的黑壳，黑壳可能就会因为开启了深度测试（ZTest）而出错，或者直接把身体覆盖掉。

*（进阶提示：像“毛发渲染”经常会写七八个一样的 Pass，每一层往外扩张一点点并变得更透明，这叫 Shell Rendering，也是严格从上到下叠加上去的。）*

### 情况三：传统内置管线 (Built-in) 的“无限循环” Pass

在以前的老 Unity 里，如果你用了 `LightMode = ForwardAdd` 这个暗号，执行顺序就会变得非常诡异。

因为 `ForwardAdd` 专门用来处理额外的点光源。
如果场景里有 1 盏主太阳光，和 3 盏火把（点光源）照亮了你的角色。
实际的执行顺序是：
1. 执行 `ForwardBase` Pass（画出太阳光和基础颜色）。
2. 执行 `ForwardAdd` Pass（计算火把 A 的光，**叠加**进屏幕）。
3. **再次**执行刚才的 `ForwardAdd` Pass（计算火把 B 的光，**叠加**进屏幕）。
4. **第三次**执行 `ForwardAdd` Pass（计算火把 C 的光，**叠加**进屏幕）。

你看，同一个 Pass 被循环调用了 3 次！这是最耗费性能的“多 Pass 噩梦”，也就是为什么场景里光一多手机就发烫。
*(注：URP 管线为了解决这个问题，把光源计算改成了单 Pass 内的 For 循环，彻底抛弃了 ForwardAdd)*。

---

### ⚠️ URP 时代的警告：慎用自定义多 Pass！

既然情况二（写两个没有特定 LightMode 的 Pass）可以做描边，为什么现在的大佬都不建议这么写了？

因为在 URP（通用渲染管线）中，**SRP Batcher（超级合批优化神技）极度讨厌同一材质里的多 Pass！**
如果你为了做描边，在 Shader 里手写了两个画颜色的 Pass，这个材质就会**直接打破** SRP Batcher，导致 DrawCall 暴增，性能大幅下降。

**现在的正规做法是：**
只在 Shader 里写 1 个正常画物体的 Pass。
如果你想画描边，去 C# 端写一个 `Renderer Feature`（渲染特性），通过 C# 指挥显卡：“请把这个白模再用那个带黑色的描边材质给我再画一遍。”
把业务逻辑交给管线控制，而不是强塞进一个 Shader 文件里。

### 总结教条：如何验证？
不要靠猜！
打开 Unity 菜单栏：`Window` -> `Analysis` -> **`Frame Debugger` (帧调试器)**。
点击 `Enable`，你能看到显卡在这一帧里，第一步画了什么，第二步画了什么，用的到底是哪个 Shader 的哪个 Pass。这是图形程序排查顺序问题的**唯一真理**！
