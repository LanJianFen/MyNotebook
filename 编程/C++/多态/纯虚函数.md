

纯虚函数（Pure Virtual Function）在 C++ 中通过在函数声明的末尾加上 `= 0` 来表示（例如：`virtual void Update() = 0;`）。

如果说普通的虚函数是为了“允许子类重写修改”，那么**纯虚函数的核心意义就是定义“契约（Contract）”和“接口（Interface）”。**

具体来说，纯虚函数有三大核心战略意义：

### 1. 强制子类必须实现（编译器级别的强制约束）
普通的虚函数（比如 `virtual void Init() { ... }`），父类会提供一个默认实现。如果子类不去重写它，编译器也无所谓，大不了运行时调用父类的默认代码。

但**纯虚函数等于父类摊牌了：“这个功能我根本不知道该怎么做，你（子类）如果想作为真实存在的对象，就必须自己写出具体的代码！”**

以我们的 Hazel 引擎为例，假设未来我们在引擎内部写了一个生命周期函数：
```cpp
class Application {
public:
    // 普通虚函数：引擎可以给个默认逻辑，子类爱改不改
    virtual void OnWindowResize() { /* 默认调整内部视口大小 */ } 

    // 纯虚函数：引擎绝不知道你的游戏每帧要更新什么逻辑，子类必须实现！
    virtual void Update() = 0; 
};
```
如果你在 `Sandbox` 游戏里忘记写 `Update()` 函数了，**编译器会直接报错，拒绝编译**。这种机制在大型团队协作或引擎开发中极其重要，它通过编译器保证了“只要你能跑起来，你就一定写了必须写的代码”。

### 2. 制造“抽象类（Abstract Class）”，阻止基类被实例化
只要一个类里面**包含至少一个**纯虚函数，这个类在 C++ 中就会自动降级为**抽象类**。

抽象类在语法上的唯一特权（或者说限制）就是：**绝对不允许被直接实例化（不能 `new` 出来）**。
```cpp
Application* app = new Application(); // ❌ 编译直接报错！因为 Application 是抽象类
```
这在软件工程中是非常合理的。`Application` 只是一个概念上的“空壳引擎应用”，它在物理世界中不应该有对应的实体。真正能运行的必须是某个具体的游戏（如 `Sandbox`）。纯虚函数从语法层面上，彻底断绝了程序员误操作去实例化一个无意义基类的可能性。

### 3. 在 C++ 中完美模拟“接口（Interface）”
很多现代面向对象语言（如 Java、C#）都有 `interface` 关键字。接口的本质就是“只有函数声明，完全没有任何数据成员和代码实现”。

C++ 原生是没有 `interface` 这个关键字的，那 C++ 怎么写接口呢？
**答案就是：写一个所有函数全都是纯虚函数的类。**

比如在图形渲染中，引擎想要支持多渲染后端（OpenGL, DirectX, Vulkan）：
```cpp
// 这就是一个完美的 C++ 接口
class RendererAPI {
public:
    virtual ~RendererAPI() = default;

    virtual void SetClearColor(float r, float g, float b, float a) = 0;
    virtual void Clear() = 0;
    virtual void DrawIndexed() = 0;
};
```
引擎高层逻辑完全不关心底层是谁在画图，它只管拿着 `RendererAPI*` 这个基类指针去调用 `Clear()`。
而底层的 `OpenGLRenderer` 和 `DirectXRenderer` 则必须“签订契约”，老老实实把这三个纯虚函数全部实现了，才能被塞进引擎里运行。

---

### 总结
如果把面向对象编程比作公司架构：
*   **普通函数**：公司制定的死规矩，所有人严格执行，不能改。
*   **普通虚函数**：公司给出的指导方针，你不知道怎么做就照着公司的做，你有更好的想法可以按你的做。
*   **纯虚函数**：公司下达的 KPI 目标。公司不教你怎么做，但你**必须**交出结果，做不出来就滚蛋（编译不通过）。类本身也变成了一个只定义 KPI 不做具体实事的“抽象管理层”。
