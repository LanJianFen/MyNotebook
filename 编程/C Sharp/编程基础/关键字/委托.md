
## 上层委托类型
---

### 🤖 为什么说委托不仅是“函数指针”？

在 C 语言里，函数指针就是一个纯粹的、8 字节大小的内存地址（指向代码段）。
但在 C# 里，几乎所有的委托都继承自 `System.MulticastDelegate` 类。当你 new 一个委托时，它在堆内存（Heap）里包含了 **3 个极其核心的部件**：

1.  **`Method` (核心)**：这才是你想要的那个“函数指针”，它记录了代码存在内存里的位置。
2.  **`Target` (对象引用)**：如果你的委托指向的是一个实例化对象的方法（不是 `static` 的），它必须把你这个对象也存下来（也就是 `this` 指针）。否则等回调发生时，代码根本不知道是哪个对象的属性在改变！
3.  **`InvocationList` (调用列表)**：这是 C# 委托的杀手锏。C# 的委托天生是**“多播（Multicast）”**的，它内部维护了一个链表（或数组）。你可以用 `+=` 往这个链表里塞入十几个函数，触发时它会自动把这十几个函数按顺序全执行一遍！

> **结论**：C# 的传统委托是一个**分配在堆内存上的重量级对象**（产生 GC），它 = `代码地址` + `对象上下文` + `链表结构`。

### 📦 现代 C# 的“委托三剑客”

在上古时代，我们要用委托，还得自己写一行恶心的定义：`public delegate void OnPlayerDeath(int score);`。
现在已经是 2026 年了，这种自定义委托早就被扔进了历史垃圾堆。微软为我们预定义好了**“三剑客”**，涵盖了 99.9% 的需求：

#### 1. `Action` 家族（只做事情，不求回报）
*   **本质**：所有**没有返回值（void）**的委托。
*   **参数**：最多支持 16 个参数：`Action<T1, T2 ... T16>`。
*   **示例**：
    ```csharp
    // 接收一个 int 和一个 string，但不返回任何东西
    Action<int, string> onDamageTaken = (damage, source) => 
    {
        Debug.Log($"受到 {source} 的 {damage} 点伤害");
    };
    onDamageTaken?.Invoke(50, "火球术");
    ```

#### 2. `Func` 家族（拿钱办事，必须给结果）
*   **本质**：所有**必须有返回值**的委托。
*   **规则**：泛型列表里的**最后一个类型**，永远是它的返回值类型！
*   **示例**：
    ```csharp
    // 接收两个 float（x, y），返回一个 bool
    Func<float, float, bool> checkDistance = (x, y) => x * x + y * y < 100;
    
    bool isClose = checkDistance(5f, 5f); 
    ```

#### 3. `Predicate<T>`（专职安检员）
*   **本质**：其实就是 `Func<T, bool>` 的特化版。它只能接收**一个**参数，并必定返回 **bool**。
*   **适用场景**：专门用于 List、数组的条件搜索（如 `Find`, `FindAll`, `RemoveAll`）。
*   **示例**：
    ```csharp
    List<int> enemiesHP = [10, 50, 0, 100, 0];
    
    // 找出所有血量为 0 的敌人
    enemiesHP.RemoveAll(hp => hp <= 0); // 这里的 lambda 就是一个 Predicate
    ```

### ⚡ 真正属于 2026 年的黑科技：C# 的“裸·函数指针”

前面说了，`Action` 和 `Func` 都是对象，会产生 GC Alloc，调用时还要经过 `Invoke` 的虚方法路由。
如果在 Unity 的 **Burst 编译器**、**ECS 架构**，或者每秒执行百万次的图形计算中，委托的性能开销是不可接受的！

这时候，你在问题里提到的**“本质就是函数指针吧？”** 终于迎来了终极答案！

在现代 C#（C# 9.0 以后）中，微软为了榨干 CPU 的最后一滴性能，引入了真正的 C++ 级别的函数指针——**Unmanaged Function Pointers (非托管函数指针)**。

它的语法是 **`delegate*`**（注意那个星号，看着就极其硬核）：

```csharp
// 必须在 unsafe 块中使用，因为它就是赤裸裸的内存地址！
unsafe class MathOptimized 
{
    // 定义一个真正的函数指针：接收两个 float，返回 float
    // 这里的 managed 代表调用 C# 方法，unmanaged 可以直接调用 C++ 的 dll 方法！
    public delegate* managed<float, float, float> mathOperation;
    
    public static float Multiply(float a, float b) => a * b;

    public void Run() 
    {
        // 直接把函数的内存地址赋给指针，不 new 任何对象！0 GC！
        mathOperation = &Multiply; 

        // 像 C 语言一样直接通过指针调用！没有 Invoke 开销！
        float result = mathOperation(10f, 5f); 
    }
}
```
**在 Unity 2026 的实战意义：**
如果你在写 Burst 编译器下的 Job（多线程任务），传统的 `Action` 是绝对被禁止的（因为托管对象不能跨线程共享且不符合 Blittable 内存连续性）。
此时，你只能用 `delegate*`！它让 C# 拥有了真正媲美 C++ 的极致底层回调能力。

## event 关键字
我必须立刻纠正你一个天大的误解：
**你以为普通的 `Action` 只能装 1 个函数，加了 `event` 才能装很多个？**
**错！大错特错！**

真相是极其颠覆的：**在 C# 里，哪怕是不加 `event` 的、最普通的 `Action`，它天生就能装下无数个函数！**

来，我们一层一层把你大脑里的这个“结”彻底解开。

---

### 🧬 真相一：所有的委托，天生都是“链表”！

在 C/C++ 里，一个函数指针确实只能指着一个函数。
但在 C# 里，微软做了一个极其变态的设计：**所有的委托（包括 `Action`, `Func`, 以及你自定义的 `delegate`），在底层全部自动继承自一个叫 `System.MulticastDelegate`（多播委托）的类！**

“多播”是什么意思？就是**单向链表**。

我们来看看**不加 `event`** 的纯粹 `Action` 是怎么工作的：
```csharp
public class MyTest
{
    // 注意：这里没有 event！只有一个纯粹的 Action 变量！
    public Action OnTest; 

    public void DoTest()
    {
        // 绑定第 1 个函数
        OnTest += () => Debug.Log("我是功能 1"); 
        
        // 绑定第 2 个函数
        OnTest += () => Debug.Log("我是功能 2");

        // 一旦调用...
        OnTest.Invoke(); 
        
        // 【结果】：两行 Log 都会打印！它天生就能装下很多函数！
    }
}
```
**结论：** `Action` 本身就是一个自带 `+=` 拼接功能的“函数容器”，它根本不需要字典，它自己就是一条链子！

---

### 💥 真相二：既然 Action 能装很多函数，为什么还要加 `event`？

这就要回到我们之前聊过的**“安全问题”**了。

假设你写了一个玩家类，里面用了一个**裸的 `Action`**：
```csharp
public class Player 
{
    // 裸的 Action 容器
    public Action OnDeath; 
}
```

现在，UI 系统跑过来，把自己装进去了：
```csharp
// UI 系统：我用 += 把自己加进了链表！
player.OnDeath += ShowGameOverUI;
```
接着，音效系统跑过来，把自己装进去了：
```csharp
// 音效系统：我也用 += 把自己加进了链表！现在链表里有 2 个函数。
player.OnDeath += PlayDeathSound;
```

**这时候，灾难发生了！**
公司新来了一个实习生，他写了一个“成就系统”，他也想监听玩家死亡，但他忘记写 `+` 号了，他直接用了一个等号 `=`：
```csharp
// 实习生：写错代码了...
player.OnDeath = UnlockDeathAchievement;
```

**发生了什么？**
因为你暴露的是一个毫无保护的 `Action` 变量，这个等号 `=` 会**直接把之前 UI 和音效辛苦建立的链表全部砸碎、覆盖掉！** 
现在这个容器里，只剩下实习生的这 1 个函数了。当玩家死亡时，UI 不弹了，音效不响了，只有成就解锁了。

---

### 🛡️ 真相三：`event` 到底是个什么神仙操作？

为了防止上述惨剧发生，微软发明了 `event` 关键字。

**`event` 根本不改变 `Action` 装载函数的数量，它的唯一作用，就是“剥夺外部类使用等号 `=` 的权利”！**

当你写下这行代码：
```csharp
public static event Action<T> OnEvent;
```
编译器在底层会把它强行拆解成两部分：
```csharp
// 1. 偷偷生成一个绝对私有的 Action 链表容器（只有总线自己能碰）
private static Action<T> _onEvent;

// 2. 对外暴露两个严格的方法（就好像属性的 get 和 set）
public void add_OnEvent(Action<T> value) 
{ 
    _onEvent += value; // 只能往里加
}

public void remove_OnEvent(Action<T> value) 
{ 
    _onEvent -= value; // 只能往外拿
}
```

**这就是 `event Action<T> OnEvent;` 的全貌！**

加了 `event` 之后，实习生如果再敢写 `EventBus.OnEvent = UnlockAchievement;`，**编译器会直接亮红线报错**：
❌ *"事件 OnEvent 只能出现在 += 或 -= 的左边 (从类型 EventBus 外部使用时)"*

## delegate 关键字

```csharp
public delegate void DamageHandler(float amount, Vector3 position); 
```

当我们写下这一行的时候，我们的预期是生成一个DamageHandler函数指针封装类型，这个类型接受的参数是float和vector3。

现在有了这个类型，我们要去使用它，就要写

``` CSHARP
public DamageHandler onDamage
```

它就像Action一样可以一直 +=，我们可以给它加上event，防止=。

---

### 🎯 完美闭环的代码演示

#### 第一步：制造“类型”（用 delegate 关键字）
正如你所说，这一步我们是在向编译器下指令，生成一个专属的“函数指针封装类”。
```csharp
// 制造了一个名为 DamageHandler 的类型，专门接收 float 和 Vector3
public delegate void DamageHandler(float amount, Vector3 position);
```

#### 第二步：使用“类型”声明变量（裸奔版 vs 防弹版）
现在我们有了 `DamageHandler` 这个类型，我们可以像用 `Action` 一样去用它：

**【裸奔版：不加 event】**
```csharp
public class Player
{
    // 就像 public Action<float, Vector3> onDamage 一样
    public DamageHandler onDamage; 
    
    void Test()
    {
        // ❌ 外部脚本可以为所欲为
        player.onDamage += UI_Update;      // 合法
        player.onDamage = Achievement_Get; // 合法！UI 和音效全被清空覆盖！致命漏洞！
        player.onDamage.Invoke(99, pos);   // 合法！外部可以假传圣旨！
    }
}
```

**【防弹版：加上 event】（回答你的问题：完全可以，而且必须这么做！）**
```csharp
public class Player
{
    // 加上 event，瞬间罩上防弹玻璃！
    public event DamageHandler onDamage; 
    
    void Test()
    {
        // ✅ 外部脚本只能乖乖听话
        player.onDamage += UI_Update;      // 合法，允许订阅
        
        // ❌ player.onDamage = Achievement_Get; // 编译报错！绝不允许使用 = 覆盖！
        // ❌ player.onDamage.Invoke(99, pos);   // 编译报错！绝不允许外部主动触发！
    }
}
```

### delegate 的本质

当你敲下那行短短的代码并按下编译键时，C# 编译器会在底层把它“膨胀”成类似下面这样的一长串代码：

```csharp
// 编译器自动生成的隐藏代码，完全等价于你写的那行 delegate
public sealed class DamageHandler : System.MulticastDelegate
{
    // 1. 构造函数：负责接收“要绑定的对象”和“函数的内存指针”
    public DamageHandler(object target, IntPtr methodPtr) 
    { 
        // 底层逻辑... 
    }

    // 2. 核心方法：名字叫 Invoke，参数和你定义的一模一样！
    public virtual void Invoke(float amount, Vector3 position)
    {
        // 遍历底层的多播链表，逐个执行函数...
    }

    // (在老版本的 .NET 中还会生成 BeginInvoke 和 EndInvoke 用于异步，
    // 但在现代 .NET Core/Unity 现代运行时里已经废弃不用管了)
}
```


看到了吗？这就是为什么我在前面反复强调“委托不仅是函数指针，它是穿着机甲的类”的原因！

当你定义一个 `delegate` 时，本质上发生了这 4 件事：

#### 1. 你定义了一个全新的“引用类型 (Reference Type)”
因为底层是一个 `class`，这意味着一旦你实例化它（比如 `DamageHandler handler = myPlayer.TakeDamage;`），它就会在**堆内存（Heap）上分配空间**，并且最终会由垃圾回收器（GC）来清理。

#### 2. 它天生自带“多播（链表）”能力
看到它继承的 `System.MulticastDelegate` 了吗？这就是我们在上一回合聊的，为什么它可以不停地 `+=` 的根本原因。这个父类在底层维护了一个数组/链表，专门用来装载多个函数的指针。

#### 3. 编译器为你量身定制了 `Invoke` 方法
你之所以能写 `handler.Invoke(10f, Vector3.zero)`，或者直接写 `handler(10f, Vector3.zero)`，是因为编译器把你定义的参数 `(float amount, Vector3 position)`，**原封不动地搬到了生成的 `Invoke` 函数里**。这就保证了绝对的**类型安全**——如果你少传一个参数，或者传错类型，编译直接报错。

#### 4. 为什么微软要把它伪装成一句极简的代码？
想象一下，如果每次你想写一个回调函数，你都必须手动写上面那一长串 `class`，还要自己处理函数指针和链表……你会疯掉的。
所以 C# 提供了 `delegate` 这个语法糖关键字。**你只管写一行声明，剩下的脏活累活，编译器全包了。**

### 历史的发展：先有 delegate，后有 Action

如果倒退回 2002 年，当时的 **C# 1.0** 刚刚诞生，那时候**根本没有**泛型，也**根本没有** `Action` 和 `Func`！

在那个荒荒蛮时代，所有程序员不管要写什么回调，都**必须**亲自用 `delegate` 关键字手写图纸。
```csharp
// C# 1.0 时代，就算你只需要传一个 int，你也得自己定义
public delegate void MyIntAction(int target);
public delegate void MyStringAction(string text);
```

直到后来的 **C# 3.5**（伴随 LINQ 的诞生），微软实在看不下去了，他们觉得：“全世界的程序员每天都在用 `delegate` 写这堆无聊的、重复的图纸，太浪费时间了！”

于是，微软的工程师决定**自己动手**。他们打开 C# 的底层系统代码，用 `delegate` 关键字配合刚刚发明的泛型 `<T>`，一口气写下了 16 个标准图纸：
```csharp
// 微软源码里的真实操作：
public delegate void Action();
public delegate void Action<T>(T obj);
public delegate void Action<T1, T2>(T1 arg1, T2 arg2);
// ...一直写到了 T16
```
就这样，**`Action` 和 `Func` 诞生了。**它们根本不是什么新魔法，它们只是微软用最原始的 `delegate` 关键字，帮你提前“量产”好的**标准件**。
